# Cogitate — Project Context

## Architecture

- **Backend**: FastAPI (Python 3.14) in `backend/app/`
  - API routes at `backend/app/api/v1/`
  - Domain models at `backend/app/domain/`
  - Database models at `backend/app/infrastructure/database/models.py`
  - Pipeline components at `backend/app/services/cognitive_pipeline/`
  - Uses `uv` for package management
- **Frontend**: React + Vite + TypeScript in `frontend/src/`
  - DaisyUI for UI components
  - Zustand for state management
  - Pages at `frontend/src/pages/`
  - Components at `frontend/src/components/`
  - Stores at `frontend/src/stores/`
- **Database**: SQLite via SQLAlchemy (async, aiosqlite driver)
  - Main DB: `cogitate.db`
  - Traces DB: `data/pipeline_traces.db`
  - Cognitive memory: `data/cognitive_memory.db`
  - Documents: `data/cogitate_docs_en.db`

## Key Conventions

- **Python style**: type hints everywhere, async/await for I/O
- **Testing**: pytest with asyncio_mode=auto
  - Fast suite: `python3 scripts/testing/run_tests.py --group {unit,workflows,api,components} --parallel`
    from the project root — the four fast groups in ~3 min. A bare serial `pytest` over the same
    tests takes 20+ min and shows no progress. One module while working:
    `run_tests.py --file tests/unit/foo.py`
  - Full sweep: `python3 scripts/core/sweep.py backend` from project root
- **Test runs**: one run is ONE FOLDER under `data/test-runs/<name>/`
  (`report.md`, `report.xml`, `events.jsonl`), written by
  `scripts/testing/run_tests.py`. The RUNNER owns the lock beside them
  (`.run.lock`), so a terminal run, a page run and a sweep run collide through one
  mechanism — one run at a time, never two. The user-testing page
  (`/testing-dashboard`) starts, watches, cancels and retires them;
  a deleted run MOVES to `trash/test-runs/<name>` rather than vanishing.
- **Naming**: use 'sqlite' not 'disk'; 'memory vs storage' not 'memory vs disk'
- **Confirmation messages**: use the app's toaster notification system (useNotificationStore), not inline alerts
- **Modal components**: must use `<dialog className="modal">` wrapper for DaisyUI v5
- **Frontend modes**: `./cogitate.sh mode development|production` — or the mode switch on
  the dashboard. **Development is for frontend WORK; production is for using the app the
  way a user would.** Both serve the **same port** on purpose: auth, the persisted stores
  and the cross-tab channel are origin-scoped, so a second port would sign the user out.
  It is **frontend only** — the backend is never cycled — and a failed build aborts before
  anything stops. In production an edit is invisible until the bundle is rebuilt; the
  dashboard's `DEV`/`PROD` badge is what tells a stale bundle from a broken one.
  Detail: `wiki/dev-notes/lifecycle/starting.md`.

## Session Workflow

1. Work on goals defined in `local/sessions/session_plan.md`
2. Track progress in `local/sessions/status_report.md`
3. At session end: roll files with `python3 local/scripts/file_roller.py local/sessions/session_plan.md`
4. Create fresh `session_plan.md` and `status_report.md` for next session
5. The new status file starts with a summary of the previous session
6. The new session plan outlines the next session goals

### Session Numbering Convention
- Sessions are numbered **when archived**, not when created.
- Active files have no number: `local/sessions/session_plan.md`
- The roll numbers them IN PLACE (`session_plan_37.md`; `local/scripts/file_roller.py`, always max + 1), and the
  series is then consolidated into `_archive/sessions/<date>/` — `local/sessions/` holds only the live
  unnumbered pair.
- **After a consolidation the numbering restarts at `_01`, by design**: the roller scans the live directory
  only, and an emptied directory IS the reset. A surprisingly small next number is intended — never "repair"
  it by scanning `_archive/`.
- Do NOT include session numbers in filenames or content — the file_roller handles that.
- DO NOT commit `local/sessions/` or `local/reports/` files to git.

## Todo Management

Todo items live in `todo/master.md` — local working notes, **not tracked** (`todo/` is gitignored,
beside `local/`). They ship nowhere; the repo carries the product, not the backlog.

### Todo Process
- **The roll maintains it — standing ruling (2026-10-05, amended 2026-10-15).** At every roll, unasked, the agent corrects existing items to match what landed (headline status, a **Landed so far** paragraph) and files a finding the session's own work raised, newest-first under the banner. Those no longer need a per-wrap ask.
- **The roll also retires and splits (2026-10-15 — the census found 21 closed items sitting in an open list).** Two structural dispositions, and no others:
  - **retire a CLOSED item** — move it, text preserved verbatim, to `todo/done/<workstream>.md`, instead of adding another "landed" paragraph to it. The closure is MEASURED, never read off the heading: its commits verified against `git log`, or a named check run at the move. Where a closure cannot be verified, the done file's header says so rather than passing it as verified.
  - **split a HALF-OPEN item** — the closed half's record to `todo/done/`, the open half into its own item whose heading NAMES that half. A split creates no work the item did not already carry, and loses nothing: every paragraph of the original lands in exactly one place.
- **Still needs the user's word:** removing an item, adding/renaming/merging a section, re-ordering the list, and retiring an item the roll cannot verify.
- **Never** reorganize, rename or merge sections to "tidy", and never delete an item.
- **Git commit**: Nothing under `todo/` is committed — it is ignored. The roll's todo edits stay local; the
  audit trail for them is the roll's status report in `local/sessions/`, not `git log`.
- **Archived**: Old completed sprints can be moved to `_archive/` when they're no longer relevant
